# Local draft authority interface

`settletable.authority` owns one-host SQLite meal state. The external seam is `Authority(path, *, clock=time.time, failure_hook=None)`, `bootstrap`, `snapshot`, `apply`, `issue_invitation`, `redeem_invitation`, `rotate_session` and `close`. It raises `AuthorityError` with a safe stable `code`; it never returns raw storage exceptions. Inputs and outputs are exact frozen slotted dataclasses and exact tuples. Constructors alone do not validate facts.

`bootstrap(meal_id, participants, *, session_ttl=3600)` accepts a tuple of `Participant(id, name, organizer=False)` with exactly one organizer. It returns `BootstrapResult(meal_id, sessions)`, containing one `SessionGrant(participant_id, credential)` per participant. Credentials appear only in that one-time trusted return, are omitted from its representation, and are never persisted. This is trusted local provisioning, not account registration.

### Invitation & Session Lifecycle:
- `issue_invitation(organizer_credential, meal_id, participant_id, *, invite_ttl=86400, issue_id=None)`: Authorized organizer issues a single-use expiring invitation for an active diner. Returns `InvitationGrant(meal_id, participant_id, token, expires)`. Tokens are 43-character base64url strings from 32 CSPRNG bytes, omitted from repr, with domain-separated verifier `settletable-invitation-v1\0` persisted in SQLite. At most one active unexpired unrevoked invitation is permitted per participant.
- `redeem_invitation(invitation_token, meal_id, *, session_ttl=3600)`: Invitee redeems a single-use invitation. In a single SQLite transaction, marks invitation consumed, atomically rotates/replaces any prior session verifier for that participant, and returns `SessionGrant(participant_id, credential)`.
- `rotate_session(credential, meal_id, *, session_ttl=3600)`: Authenticated participant rotates their own session. Overwrites the session verifier atomically. Does not advance `meals.revision`, preventing false concurrency conflicts on financial drafts.
- Lifecycle operations are bounded to 64 generations per participant, rejecting further issuance/rotation with `resource_limit`. Security revocations remain strictly available even when lifecycle or ordinary 10,000 command quotas are exhausted.

`snapshot(credential, meal_id)` returns the entire consistent immutable `DraftSnapshot`; `apply(credential, meal_id, command)` returns `AcceptedResult` only after commit. `close()` closes the connection.

Receipt facts: `ReceiptItem(id, label, quantity=1, line_sen=None)`, `ReceiptAdjustment(id, label, kind, amount_sen, eligible_item_ids, rationale)`, and `Receipt(items=(), subtotal_sen=None, total_sen=None, adjustments=(), included_tax_sen=0)`. Monetary values are integer sen or documented unknown `None`. Quantities are exact `int`/`Fraction`; adjustment scopes are nonempty tuples. Receipt review does not invent diner allocations.

Commands (positional order shown; keywords recommended):

- `ReplaceReceipt(command_id, expected_revision, expected_financial_revision, receipt)`
- `SetOwnQuantity(command_id, item_id, quantity, expected_item_revision, expected_financial_revision)` (`None` releases)
- `ReviewReceipt(command_id, expected_revision, expected_financial_revision, receipt_digest)`
- `Finalize(command_id, expected_revision, expected_financial_revision)`
- `RevokeSession(command_id, expected_revision, participant_id)`
- `RevokeMembership(command_id, expected_revision, participant_id)`
- `RevokeInvitation(command_id, expected_revision, participant_id)`

`DraftSnapshot` exposes meal/financial revisions, receipt digest/facts, `items` as `ItemState(item_id,item_revision)`, immutable `claims` as `Claim(item_id,participant_id,quantity,financial_revision,status)`, current review, finalized calculation, diagnostics, fixed participants, inactive participant IDs, and `invitations` as `InvitationRecord(participant_id,created_at,expires,consumed,revoked,issue_id)` ordered deterministically. A claim status is `confirmed` or `pending`. `ReviewRecord` records participant ID, financial revision, receipt digest and command ID. `AcceptedResult` exposes command ID/kind, original committed revisions, changed claims, optional actual calculator result and `canonical_bytes`. Those bytes are the durable exact response; exact authorized retries return identical bytes and original revision, not a current snapshot.

Trusted `failure_hook(stage)` can raise at `after_state`, `after_result`, `before_commit`, or `after_commit`. Precommit exceptions roll back both state and response. An `after_commit` exception reports `commit_uncertain`; retry the identical command. Hooks receive no credentials or state. They are trusted test dependencies, not an untrusted callback facility. Database administrators and privileged Python callers remain outside this permission guarantee.

Commands and accepted results are at most 1MiB of canonical JSON. Ordinary state mutations additionally retain a 900,000-byte state ceiling, leaving security-revocation headroom below the 1MiB storage ceiling. State/response limits reject before commit without pruning earlier accepted history. A failed rollback discards the connection; reopen through a new `Authority` before further work.

Errors are raised, not returned. `invalid_input` rejects malformed typed facts; `invalid_session` covers unknown, expired, revoked or wrong-meal sessions without explaining the private cause; `invalid_invitation` covers unknown, expired, malformed, consumed or revoked invitation tokens; `active_invitation_exists` rejects issuing duplicate active invitations for the same diner. `forbidden` rejects current command permissions before replay lookup. `command_conflict` rejects an accepted ID with changed canonical content. Revision conflicts distinguish `revision_conflict`, `financial_revision_conflict` and `item_revision_conflict`; refresh a snapshot before a new command. Receipt/claim diagnostics also serve as rejection codes, including `missing_receipt`, `missing_amount`, `subtotal_mismatch`, `receipt_total_mismatch`, `discount_over_base`, `zero_base`, `pending_claim` and `incomplete_quantity`. `review_required`, `receipt_digest_conflict`, `quantity_capacity`, `claimed_item_deletion`, `retired_source`, `source_kind_conflict`, `claim_missing`, `unknown_item`, `finalized`, `already_revoked`, `resource_limit` and `calculation_rejected` name the remaining business rejections. `meal_exists` prohibits bootstrap reset. `busy` is retryable after a bounded lock wait; `storage_error` is a safe storage/dependency failure; `commit_uncertain` requires identical-ID retry or a current snapshot rather than inventing a replacement mutation. Dependency exception messages are never forwarded. Input errors and rejections are not saved as accepted history.

Every receipt replacement advances financial revision and clears review, even if the supplied facts equal the previous version. New or changed item definitions advance their item revisions; unchanged definitions retain theirs. Deleted source IDs are retired permanently in this local store; corrections may update an existing line, but deleted identities cannot be recycled into another line. Revoking a session or membership cascades to invalidate outstanding active invitations for that participant; already-revoked targets reject without inserting audit rows. New financial participants, account recovery and external transports are outside this interface. Expiry compares the trusted clock with the persisted expiry using an exclusive upper bound.

No networking, browser UI, settlement, OCR or Notion is included. Read the binding specifications for bounds, permission/replay ordering, pending ownership and deferred policy gates.
