## Recommended smallest coherent progression

**Proposal:** scope the next implementation to an integrated local invitation/session lifecycle for **already declared diner identities**, with trusted local organizer provisioning. Follow it with a separately reviewed same-origin HTTP adapter. This advances the missing Internet-access seam without conflating account recovery, automatic person matching, financial participant changes, or public hosting. If the orchestrator instead combines these into one transport slice, retain the same independent gates and small commits; do not label a transport-only wrapper complete invitation security.

The first local lifecycle contract should have a small interface: issue/revoke an invitation under current organizer authority; redeem a bounded token into the predetermined diner identity; authenticate through the resulting session; explicitly expire/revoke it. Bootstrap stays trusted and must not become anonymous remote meal creation. Invitations confer no organizer role, contain no caller-chosen participant/role override, and never grant data access before successful redemption. A display name is not identity proof. Invited bearer possession proves control of the capability, not the named human; this limitation must be visible before a real product uses names for attribution.

Use fresh high-entropy invitation tokens, separate domain-separated verifiers, explicit expiry and one-use state. Bind invitation rows to meal plus stable intended participant and issuer; bind issued sessions to that same membership. Give token inputs their own strict type/alphabet/length checks before hashing or database work. Choose bounds and test TTL defaults as engineering settings, not irreversible product preferences. No raw invitation/session belongs in command history, ordinary snapshot, log, exception, trace, database, test failure message or checked-in fixture.

**Do not compose two independent stores.** Checking an invitation in one database and then invoking `bootstrap` or `apply` against the authority file creates a redemption/revocation race and an orphan-credential failure window. Invitation consumption, current issuer/member checks, session issuance/rotation and their accepted effects need one authority-owned SQLite transaction. Do not emulate this by reaching into `_db` from a framework handler. Factor an internal transaction seam or extend the authority interface deliberately, retaining current permission-before-replay and financial atomicity. No external work belongs inside the transaction.

One-session rotation can preserve the existing uniqueness rule, but replacement must invalidate the old verifier atomically and preserve participant-scoped financial replay identity. An expired session must not renew itself indefinitely; a revoked member must not regain access merely because an older invite or refresh capability exists. Session revocation and membership revocation must have documented distinct effects on outstanding invitations. A conservative first contract can invalidate all outstanding invitations for a revoked membership and require explicit new organizer authorization rather than implicit restoration. Restoration/recovery is not thereby authorized or selected.

**Resolve acknowledgment loss before implementation acceptance.** A one-use redemption that commits and loses its response cannot safely replay an ordinary stored response containing a raw session. Storing encrypted recoverable bearer material introduces a key-management commitment; returning a new token on every replay breaks one-use/revocation reasoning. The specification must select and test a precise safe protocol, or explicitly expose committed-but-unreceived issuance and require organizer reissue without resetting financial state. This local failure policy is not evidence of a complete account-recovery product. Renewal has the same problem. Do not claim seamless recovery merely because the existing financial commands replay.

**Recompute resource bounds.** Unlimited invitation issuance, session rotation and distinct revocation targets invalidate the old fixed two-per-person reserve argument. Choose bounded generations/history and security capacity; prove an exhausted ordinary or invitation quota cannot prevent revocation. Define what accepted replay means for invitation operations without storing secrets in canonical bodies/results. Do not silently exempt a growing class of commands from all bounds or prune durable financial results.

## HTTP/browser contract that must follow

Proposal for the eventual adapter: one origin, polling snapshots initially, no WebSocket dependency. Preserve the accepted typed command contract with a strict wire decoder: bounded body read before JSON parsing, reject duplicate object keys and unknown fields, bool-as-int/floats/noncanonical rational mistakes, actor injection and oversized headers/cookies/paths. Return stable safe codes; never forward SQLite/dependency diagnostics. An HTTP accepted result must come only after the real authority commits, and clients must distinguish historical replay from a current snapshot.

Prefer an opaque host-only `HttpOnly; Secure` session cookie with explicit SameSite policy over browser localStorage. Cookie authentication requires same-origin CSRF defenses for all state-changing routes, including invitation issuance/redemption/logout/renewal. Require a server-validated CSRF token or comparably reviewed protocol plus exact configured Origin checks; missing or `null` Origin is not automatically trusted. Reject hostile Host headers; trust forwarded host/proto/client IP only from a configured proxy, not arbitrary headers. No wildcard credentialed CORS, GET mutations, permissive developer fallback or caller-supplied redirect destination.

An invitation landing GET must not consume the capability: mail previews, scanners and browser prefetch must not spend it. A future minimal redemption page should use no third-party assets/analytics, apply `Referrer-Policy: no-referrer` and `Cache-Control: no-store`, and explicitly submit redemption. URL fragments can keep tokens out of the initial HTTP path but require a small reviewed script and do not protect a copied link, browser history or arbitrary page script. Query/path token logging is unacceptable unless every ingress log is proven to redact it. Never turn a convenient URL representation into a claim of private identity.

Use HTTPS semantics in browser tests. An in-process request test does not establish actual cookie/SameSite/CSRF behavior; test two real isolated browser contexts and hostile origins locally before clearing that gate. A loopback-only HTTP fixture must be explicitly bounded and must not weaken the eventual secure-cookie contract. SQLite connections must be created/used within their owning thread or an explicit reviewed concurrency design; a convenient global connection with disabled thread checks is not a substitute for transaction ownership.

Require bounded attempts, request size and connection concurrency before exposure. Process-local rate limiting can support local tests but is not a multiworker deployment guarantee. Trusted proxy/IP parsing, brute-force limits, secret-free access logs, TLS and operational ingress configuration need deployment-specific evidence. None is authorized by a local slice passing.

## Independent acceptance challenge

These are **proposed tests**, not executed results:

1. Two independent connections redeem the same invitation simultaneously: one issuance only, no duplicate session/membership and no split commit. Retry/response-loss behavior follows the exact selected protocol without raw-secret persistence.
2. Race redemption/rotation against invitation, session and membership revocation in both serialization orders. No old capability restores a revoked financial identity or bypasses current authorization/replay checks.
3. Wrong meal/participant, invented role, expired/unknown/malformed token, previously consumed token and changed request identity fail safely without revealing meal data. Labels cannot change identity binding.
4. Inject failures before consumption, after session change and before/after commit; reopen with independent connections. All state changes are atomic; uncertain outcomes are explicit. Raw tokens are absent from SQLite file/sidecars/dumps/results/logs/test diagnostics.
5. Existing saved financial accepted responses remain byte-identical across renewal/rotation/reopen and still require current access. Calculator source and deterministic allocation vectors are unchanged.
6. Exhaust configured ordinary and invitation/session-generation capacities, then revoke access successfully without unbounded security-history growth or deleting financial history.
7. Browser follow-up: two independently authenticated diners exercise real snapshots/claims; stale revisions and retry remain explicit; cross-origin POST, missing/null Origin, hostile Host/forwarded headers, GET redemption, cookie overwrite, duplicate JSON keys and oversized body/header inputs fail. No network listener is needed for the preceding identity-store tests.

No framework is selected by this challenge: compare a small maintained Python HTTP stack against the exact adapter/test requirements only when that implementation scope is ready.
