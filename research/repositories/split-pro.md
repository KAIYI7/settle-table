## Receipt flow and error handling

**Fact:** attachment-only flow: browser image compression (1920 maximum dimension, JPEG target) → configured upload-size check → authenticated `/api/upload` → Formidable size limit → Sharp decode, resize to 1200px/WebP quality 80 plus 200px thumbnail → local `uploads/<userId>/<uuid>.webp` → returned file key saved on expense → authenticated file endpoint and receipt viewer. UI shows compression/upload error toasts and progress; failed compression attempts original file if size permits. Upload errors return generic HTTP 500; temporary upload file is removed in `finally`.

**Fact:** no OCR/vision SDK, receipt parser, structured extraction schema, confidence mechanism or OCR-human correction loop was found by source/dependency search. The normal manual expense edit flow supports corrections to amount/participants and attachment, not extracted line items.

**Inference / do not reuse unchanged:** receipt serving checks only for an authenticated session and path existence/containment; the inspected handler does not check owner/group access to that particular file. UUID obscurity is not authorization. Its `startsWith(uploadRoot)` containment check also should be replaced by canonical path-relative containment if adapted. Compression/transcoding can erase faint thermal text; preserve a private original for OCR instead of feeding only this reduced receipt.

## Monetary calculation, splitting and settlements

- **Fact:** expense and participant amounts are DB `BigInt` / JavaScript `bigint`; currency metadata selects decimal digits (MYR supported). Numeric parsing/formatting is isolated in `src/utils/numbers.ts`. `BigMath.roundDiv` uses ties-to-even. Some boundary/FX routines still accept `number`/Float and weighted SHARE sums convert weights to Number: bigint storage does **not** mean every boundary is arbitrary-precision.
- **Fact:** EQUAL, PERCENTAGE (basis points), EXACT, SHARE, ADJUSTMENT, SETTLEMENT, CURRENCY_CONVERSION. Draft calculator divides with bigint truncation, validates total percentages/exact shares in UI, converts shares to signed creditor/debtor amounts, then distributes leftover pennies with a seeded shuffle. This is **not largest-remainder apportionment**. Seed is derived from candidate amounts/date rather than immutable expense ID.
- **Fact:** persisted participant rows are final signed net values; payer has paid minus own consumption, others negative consumption. Pairwise `BalanceView` derives mirrored relationships relative to the single payer. This representation should not be confused with explicit individual owed shares or multi-payer payment facts.
- **Fact:** settlement UI creates a `SETTLEMENT` expense with two opposing signed rows and allows partial amounts. Soft deleting/editing source expenses changes derived balances. Optional debt simplification processes each currency separately using greedy creditor/debtor matching, retaining mirrored balances.
- **Inference:** greedy function name `minCashFlow` is not a proof of globally fewest payments. Single-payer data and signed net rows make receipt explanation/multi-payer extension awkward. Use separate consumption and payments in a new shell; derive net balances.
- **Fact / boundary gap:** `createExpenseSchema` checks types but has no sum/unique participant/member/amount-magnitude refinement. Router validates write permission then forwards client-computed signed amounts to service; service relies on DB relations and does not recompute accounting. Therefore do not assume client split validation enforces server accounting invariants. New code must validate/recompute authoritative allocations server-side.

## Tests, mobile and operating costs

- **Fact:** source includes unit/component tests for numbers, split generation/recovery, simplification, currency rates, import and UI; integration tests exercise real expense/balance lifecycle, BigInt beyond `Number.MAX_SAFE_INTEGER`, transaction rollback and authorization; browser tests cover actual partial/full settlement and serialized BigInt/Date transport. CI separates fast, integration, browser and production Docker tests.
- **Fact:** responsive drawer/dialog components and PWA manifest/service worker exist. Current Playwright configuration is desktop Chromium; mobile/offline financial mutations are not proven. Mobile UX requires real viewport/device verification, especially upload and long split forms.
- **Fact:** base operating dependencies are Node hosting, persistent PostgreSQL **with pg_cron configured**, local persistent uploads volume/backups and authentication provider. Email magic links/invites require SMTP; OAuth/OIDC can replace email auth. Optional paid/incremental services include Plaid banking, legacy GoCardless, Open Exchange Rates; free alternatives and disabling integrations exist. No OCR charge in this code because there is no OCR.

## Reuse decision

**Inference:** borrow integer monetary boundaries, currency-aware formatting, explicit settlement events, derived balance views, rollback/authorization/invariant tests and partial-payment UX. Consider MIT adaptations only after tracing helper provenance; `simplify.ts` credits a GeeksforGeeks algorithm link, which merits a separate origin/license check before direct copying. Avoid pulling in banking/FX/recurrence/auth breadth merely for receipt splitting; do not reuse file-access policy, server trust in client accounting, seeded penny allocation or signed single-payer model without redesign.
