# Durable manual-entry draft authority — bounded v1

Status: **ready-for-agent — bounded local implementation authorized by the orchestrator after independent specification review.** Written2026-10-17 after the remotely verified baseline. [Decision and gates](../../docs/agents/phase-transitions.md); [independent challenge and resolutions](../../research/phase-3/authority-spec-review.md). Main objective: accept diner edits and organizer review/finalization durably, using the actual accepted calculator in the same transaction. This is one local authority module, not the complete collaborative MVP or Internet authentication.

Binding context: [MVP C1–C4](../../research/phase-2/mvp-specification.md), [calculator interface](../../docs/calculation-interface.md), [glossary](../../GLOSSARY.md), [governance](../../docs/agents/governance.md). Existing [browser](../../research/phase-2/collaboration-validation.md) and [transaction](../../research/phase-2/transaction-validation.md) probes establish limited feasibility; do not transplant their trusted-actor controllers or alternate rounding logic. Accepted `tabwise.calculation` remains unchanged unless a separately reviewed defect requires it.

## Problem, scope and explicit exclusions

Correct arithmetic does not prevent lost claims, duplicate mutations, stale review or unauthorized finalization. A saved claim and its exact accepted response must commit together, with permissions and current financial facts checked by the authority.

**This first authority subscope:** fixed participants provisioned locally; organizer enters item quantities/line amounts and scoped printed adjustments; diners set/release their own exact-rational quantity claims; organizer records review and finalizes a reconciled meal. Quantity claims cover individual/shared items without multiplying line totals. The pure calculator retains all five modes, but collaborative equal/weight/percent/exact editors and explicit charge overrides are later subscopes; no mode is silently converted to quantity.

**Excluded:** HTTP/network listeners, browser/UI/framework, Internet invitation redemption, account login/recovery/handover, adding/removing financial participants after bootstrap, finalized-meal amendments, payers/settlements, images/OCR/retention, Notion, deployment and external data. Revoking access does not delete a financial participant or redistribute consumption. These exclusions stage the agreed objective; they do not declare omitted workflow complete or settle user-dependent policies.

## Small public interfaces and trust model

Names describe proposed interfaces, not mandatory package structure. Use frozen typed inputs/results and exact tuples; unknown fields and mutable/arbitrary object shapes reject.

1. **Trusted local bootstrap:** create a fresh meal with stable participant IDs and exactly one organizer, plus opaque per-participant sessions. Only trusted host/test setup calls this interface; it must never become an unauthenticated remote registration endpoint. Existing meal IDs reject without reset. Session credentials are generated from at least32 random bytes; store only a cryptographic verifier plus meal/participant binding, expiry and revocation state. Return raw credentials once to the trusted caller, never in meal snapshots, command bodies, replay results, logs or test artifacts. Bootstrap/setup failure rolls back completely. This setup is not a resumable diner command or proof of real human identity.
2. **Accepted commands:** `apply(session_credential, meal_id, command) -> AcceptedResult | AuthorityError`. Actor/role comes exclusively from current persisted session and membership, never a body-supplied actor. Command carries stable ID, exact kind/payload and required expected revisions. AcceptedResult contains committed revision and immutable command-specific output; it contains no bearer/verifier material. Financial finalization includes the actual calculator result. An old replay result identifies its original revision; it must not masquerade as a current snapshot.
3. **Current snapshot:** `snapshot(session_credential, meal_id) -> immutable DraftSnapshot | AuthorityError`. Read a consistent committed state after checking current session/membership. Include revisions, review/finalization state, receipt facts, current/stale own-claim statuses and diagnostic issues; never expose credentials. A reconnect retrieves this snapshot and may retry an identical pending command. No event stream or automatic network recovery is promised.

The trusted host controls database path, session issuance and clock dependencies. Ordinary callers possess only opaque credentials and command inputs. A database administrator/privileged Python caller can bypass the module and is outside this permission claim. Session expiry is mandatory and checked from the trusted clock, not client timestamps. **Proposed local test setting:** configurable TTL1–86400 seconds, default3600; this does not choose future invitation/account lifetime or recovery policy. No raw capability belongs in publication fixtures.

## State and commands

Maintain separate stable financial participant IDs, access memberships, sessions, receipt items/adjustments, claims, review record, finalized calculation and accepted commands. Initial draft may lack items/totals; missing is `None`, never fabricated zero. A finalized result requires every amount and assignment required by the calculator.

- `revision`: monotonically advances once for each newly accepted mutation, including access revocation. Rejected attempts and exact replays do not advance it.
- `financial_revision`: advances on organizer receipt edits, invalidating prior review and every claim's confirmation basis. Amounts, item quantities and scoped adjustments belong to this basis.
- `item_revision`: advances on accepted changes to that item's claims or receipt definition. Distinct unchanged items may accept edits despite another item's change.
- Review record: organizer participant, current financial revision, canonical receipt digest and accepted command identity. It is an explicit authenticated attestation, not machine proof that a person physically checked a receipt. A submitted `reviewed=True` field is unsupported.
- Draft/finalized state is distinct from review validity. Incomplete/stale allocations and discrepancies remain diagnostics, never confirmed liabilities. A finalized meal is read-only for financial commands in v1; access revocation remains available.

| Command | Permission / expected basis | Accepted behavior |
|---|---|---|
| `ReplaceReceipt` | Organizer; latest meal and financial revisions | Validate bounded manual facts; persist a new receipt basis, bump financial revision and affected item revisions, clear review, preserve existing claims visibly as needing reconfirmation. Return affected claim IDs/statuses. **Conservative v1:** reject deleting an item with any retained claim; its diners must explicitly release claims first. No silent reassignment or source-ID reuse for a different line. |
| `SetOwnQuantity` | Current member; current target item revision and financial revision | No target-person field: derive person from session. Positive bounded exact rational quantity sets/reconfirms own claim; explicit `None` releases it. Reject zero/negative/overlarge values. Atomically check sum of current-basis confirmed quantities does not exceed item quantity. Older-basis claims remain visible/pending and block finalization until reconfirmed or released; they are not silently treated as zero consumption. |
| `ReviewReceipt` | Organizer; latest meal/financial revisions and exact current receipt digest | Require complete known receipt facts and no receipt-component mismatch; record the authenticated organizer attestation. It may precede complete diner assignment; it does not finalize. No automated command marks human review for the caller. |
| `Finalize` | Organizer; latest meal/financial revisions | In the same write transaction, require valid current review, no missing/stale assignments, exact complete quantity claims and no unresolved receipt issue; hydrate the accepted calculator's immutable Meal using quantity splits/scoped components, call actual `calculate`, persist its immutable result and accepted response. Any calculator rejection rolls back and leaves the draft unchanged. |
| `RevokeSession` / `RevokeMembership` | Organizer; latest meal revision | Persist revocation and revision atomically. Membership revocation invalidates all sessions through the current membership check, including duplicate-command lookup and snapshots. Financial participant/claim/history facts remain. Reject self/organizer revocation in this bounded interface; recovery/role transfer is not invented. |

Claim edits do not invalidate review of unchanged receipt amounts, but do change the meal revision, so a stale finalization attempt conflicts. Receipt edits require affected diners to reconfirm on the new financial basis. A revoked diner with a current confirmed claim retains that financial attribution; revocation grants no permission to rewrite their claim. If later receipt edits require that diner to reconfirm, the draft stays blocked rather than silently changing ownership. Restoration/removal/recovery is a later explicit scope/policy gate.

## Atomic persistence, replay and rejection contract

Use a single-host SQLite file, short write transactions and independently opened connections. No network filesystem/multiple-host database assumption. Finalized result, financial facts, revisions, review, access mutations and accepted response must share the transaction that changes them. No network, OCR or external integration work occurs inside it.

For each `apply`:

1. Validate exact input shapes/counts/lengths and bounded canonical encoding before starting costly work. Reject actor/role injection and unsupported fields.
2. Start a write transaction (`BEGIN IMMEDIATE` is the proposed serialized writer strategy); check current session verifier, meal binding, expiry, session revocation, active membership and **current permission for the command kind/target before looking up any replay**. Authorization is evaluated at this serialized acceptance point. Exact replay bypasses stale-revision and finalized-state business checks only; it never bypasses current authorization.
3. Lookup accepted command identity `(meal_id, participant_id, command_id)`. Compare canonical kind/payload/expected-revision bytes and digest. Identical accepted command returns its stored result once, even if those expected revisions are now old; changed content rejects. A different session for the same authorized participant cannot create a second application of that accepted identity.
4. For a new command, enforce permission and current applicable revisions, then validate/mutate the proposed state. Enforce item capacity and financial rules; finalization calls the real calculator here, before commit.
5. Store immutable canonical accepted body/digest/result together with state, then commit. Return only after commit. Any exception rolls back state and result together. Do not persist a fake accepted result on timeout/conflict/error.

Canonical command bytes: deterministic UTF-8 JSON with sorted keys and compact separators; exact rationals encode explicit bounded numerator/positive-denominator pairs, amounts remain integers. No floats, arbitrary class serialization or `repr` identity. Digest domain/version must distinguish this command contract from calculator rounding. Compare saved bytes as well as digest. Accepted results are append-only; normal module operations never update/delete them. Reject conflicting reuse even after newer revisions or reopen. Rejected responses are not persisted/reserved in v1; a client refresh/revision change should use a new command ID.

On a lost response, the caller retains pending status until identical retry returns the accepted response or a current snapshot clarifies state. A busy database is a bounded retryable error, not a revision conflict or success; propose at most1-second lock wait and no infinite retry in the module. Rollback/storage failure returns a safe error without raw SQL, paths, tokens or full command dumps. A commit whose success cannot be established remains uncertain to the caller; retry the same identity, never synthesize a second mutation. Closing/reopening must recover accepted state/results exactly. Exception/reopen checks do not prove power-loss resilience, backup/restore or production capacity.

## Input and output limits

Retain all calculator C1–C4 money/rational/ID/count bounds and strict boolean exclusion. Draft `None` is allowed only for documented missing monetary fields; it cannot reach final calculation. Fixed participants≤100, items≤500, scoped adjustments≤100, per-split/claim participants≤100; no source-ID collision or foreign/duplicate scope. Receipt adjustment kinds/signs/base meanings stay unchanged; require a visible label and source/reviewer rationale for every explicit receipt adjustment. This subscope accepts merchant discount facts, not prepaid/gift/voucher policy inference.

Proposed authority limits before implementation: IDs follow calculator grammar; command IDs use the same64-character grammar; display names≤80 Unicode characters; item/component labels1–160; adjustment rationale1–500; reject NUL/control characters and lone surrogates. Canonical command and accepted result each≤1MiB after structural limits, with raw-body pre-read enforcement required in any future HTTP adapter. SQLite integers/revisions must remain bounded; accepted-command count≤10,000 per meal rejects with `resource_limit` rather than deleting history. Session count is finite at bootstrap, one per participant; no renewal/invitation lifecycle is implemented here. Never publish sessions or private database snapshots in research.

### Orchestrator clarification after independent challenge

- **Credential boundary:** before hashing, encoding or database work, require an exact string of43 ASCII base64url characters generated from32 random bytes. Wrong type/size/alphabet returns a generic invalid-session error without echoing the value. Commands and credentials have separate bounds; a1MiB command limit does not bound a separate credential argument. Store only a domain-separated cryptographic verifier, never raw credentials in history or diagnostics.
- **Snapshot linearization:** check session/current membership and read all returned financial/review/revision data in one SQLite read transaction/snapshot. A concurrent revocation may serialize before or after that read; no response combines pre-revocation authorization with newer financial data from a different read snapshot. Capture the trusted authorization time at that acceptance point.
- **Pending claims:** only confirmed current-financial-basis claims reserve quantity. Earlier claims remain visibly pending and block finalization. Reconfirmation cannot displace another current claim; pending claims can always be explicitly released by their authorized owner using current revisions. Receipt replacement cannot delete a line while any retained current or pending claim exists. No implicit release or priority change.
- **Revocation under quota exhaustion:** the10,000 limit applies to ordinary financial commands, not the security-revocation reserve. With fixed participants and one session each, reserve at most two additional accepted revocations per participant (one session and one membership). Each binding can transition to revoked once; a fresh-ID already-revoked no-op rejects without a history write. Exact authorized replay remains valid. Exhausting ordinary history must not prevent either kind of organizer revocation; preserve all earlier results.
- **Local lifecycle restriction:** bootstrap/session expiry is a local acceptance-engine contract, not a complete user session/recovery product. Safe reprovisioning/renewal and actual invitation/identity policy remain prerequisites for operational application use. Receipt-only review validates known typed source facts and component reconciliation; it does not invent temporary diner allocations or claim that the full calculator has succeeded before assignments exist.

## Acceptance cases at public interfaces

Use temporary disposable databases, fixed trusted clocks and separate actual connections. Literal expected amounts come from the accepted specification/calculator cases, not a second rounding implementation. Verify through `apply`/`snapshot` and reopen; targeted transaction-failure injection may be a test seam. Tests/review must cover:

1. Bootstrap a fresh draft; existing ID cannot overwrite it; incomplete receipt remains visibly unfinalizable. Credentials/verifiers never appear in ordinary responses, persisted command bodies/results or diagnostic logs.
2. Unknown/expired/revoked/wrong-meal session denies reads and writes without disclosing another meal; body actor/role fields reject and cannot elevate a diner.
3. Diners cannot change receipt amounts/charges, review, finalize or revoke access; a session can set/release only its own claim.
4. Two independent connections race same item/financial revisions: exactly one stale write commits, no lost claim/overclaim. Fresh retry for unavailable quantity rejects; a smaller available claim succeeds.
5. Distinct unchanged items accept current item/financial revisions despite another item's accepted edit; neither participant's claim disappears.
6. Exact accepted retry returns byte-identical saved response with no new revision, even after subsequent edits; same command ID with changed payload or expected revision rejects.
7. Revocation wins before replay/read when serialized first; an old accepted response cannot bypass current session/membership. Test both ordering outcomes of revocation versus a concurrent command without claiming impossible retroactive denial.
8. Inject failure after state mutation and after accepted-result insertion: both state and response roll back, connection can transact again; rejected capacity change restores the previous claim.
9. Close/reopen and a fresh process recover the exact saved response and snapshot; lost-response identical retry does not apply twice. No OS-crash durability claim follows.
10. Organizer financial edit invalidates review and marks previous claims pending; old-financial claims reject, each diner must reconfirm/release, no automatic redistribution. Claimed-item deletion rejects with an explicit issue.
11. Current review records actor, digest and financial revision; forged boolean or stale digest/revision cannot attest. Claim edits preserve receipt review but stale the meal revision used for finalization.
12. Latest/current reviewed complete quantity1001 at1:2 finalizes through actual calculator as A334/B667; returned result and accepted response persist atomically. Complete line total is never multiplied by quantity.
13. Finalization rejects missing values, unassigned quantity, stale claims/review, and a1-sen receipt discrepancy even when earlier calculation/review succeeded; no accepted final result is saved.
14. Included-tax gross600/tax34 remains600. Scoped discount/service/SST/rounding receipt3001−101+174+290+1 finalizes to3365 using original rounded bases; full1-sen scoped discount leaves everyone zero. Compare actual calculator output, not a fixture's alphabetical tie rule.
15. Unknown/duplicate/foreign IDs, invalid signs/scopes, float/bool/oversized money or rationals, mutable inputs, overlong labels/body/results and excessive counts reject without persistent mutation; zero is distinguished from unknown.
16. A finalize command and racing claim/receipt edit serialize into an explicit current result or conflict/read-only rejection; no finalized state contains a mixture of revisions. Ordinary post-final financial commands reject; exact finalization replay still works for authorized members.
17. Session/membership revocation preserves financial identities and claims; no automatic participant removal, debt or claim rewrite. Organizer self-revocation/handover and new membership are explicitly unsupported.
18. Busy/storage/commit-uncertainty errors are distinguishable, bounded and secret-safe; no network/image/integration call occurs. Test response-size rejection before commit and history limit without pruning existing facts.
19. Credential wrong type/length/alphabet rejects before hashing/database lookup without logging raw input; snapshots concurrent with revocation have one coherent authorization/state read point.
20. Exhaust ordinary financial-command history, then verify both session and membership revocation still work within the bounded reserve; fresh-ID repeated revocation cannot grow history. Pending-claim release and reconfirmation never silently displace another current owner.

## Completion, dependencies and review questions

The orchestrator reviewed the concrete scope and the independent permission/replay/rollback/financial-composition challenge, then selected the bounded bootstrap/session seam, quantity-only first subscope, pending-claim/deletion restriction, explicit limits and canonical serialization contract above. The implementation must record red→green public-interface evidence and pass independent source/security/spec review before this slice is accepted. Specification readiness does not establish those implementation results.

Blocked future claims remain: actual Internet identity/invites/recovery, UI/HTTP defenses and escaping, joining/leaving financial allocations, other collaborative split modes, finalized amendments/settlement policy, backup/restore, real throughput/device behavior, image retention and Notion sharing. No genuine user-policy preference is chosen here; escalate only when activating the dependent feature. This spec records no phase transition and changes no production code or Git state.
